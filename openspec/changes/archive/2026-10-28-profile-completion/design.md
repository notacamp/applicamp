# Design

The `profile` module owns the data (schema `profile`). It publishes `profile.updated` (ids only) whenever a kept draft, an added skill or a reorder changes the profile, as every other write does. Every endpoint below needs a signed-in session (no scope: it is the person's own profile). A read of someone else's data is not possible: everything is by the session's account.

## Strength (code, `crates/modules/profile/src/strength.rs`)
Weights (sum 100): headline 6 · summary 8 · achievements 24 (the 3 most recent roles: each with ≥ 1 highlight = 6, a highlight with a digit or % = 8; the 24 points are shared over the recent roles there are, so one position can earn them all) · skills 12 (≥ 5 = full, proportional below) · education 6 · languages 6 · links 4 (a profile link or a site) · positions 16 (≥ 1 = 8, ≥ 3 with a start date = 16) · goals 18 (proportional to answered). Strong = ≥ 80. Each part is returned with its state (`ok|partial|missing`), what there is and what there should be (`have`/`of`, the client writes the one-line hint in its language) and an action: `question:<id>` (an open question about it), `skills`, `import`, `goals`, or `edit:<basics|work|education|languages>`. Unit-tested table.

## Profile version
`profile.profiles.version` goes up by one on every change to the data (a trigger, so no write can forget). Reviews and drafts say which version they were made from. A new profile source value `answer` marks a profile whose last change was a kept draft.

## Gap review (one model call per profile+goals version)
`complete` role, in the background (job `profile.gap_review`, enqueued by the first questions or skills request for a version; those answer 202 `running` and the client asks again every two seconds). Input: the profile as compact JSON (no name, contact details or links, positions by index) + the goals' roles and seniority. Output (strict JSON schema): `questions: [{ section (work|basics.label|basics.summary|education|links), role_ref?, question, why }]` and `skills_in_roles: [{ name, roles: [indices] }]`. `other` is not offered: an answer must have a place to go. Code validates: section exists; `work` needs a `role_ref` that exists; question ≤ 160 and why ≤ 140 characters; no question the profile already answers (a headline, summary, school or link that is there) and one per section and position; the score each question would add (`expected_gain`) is **computed by code** (strength with a result, or the section, added) and orders them, ≤ 9; ids are assigned by code. A skill is kept only if its name appears (whole word, case-insensitive; up to three letters in the same case) in at least one of the positions the model named, is not listed or dismissed, and its role count is **recounted over all positions**; ≤ 20, most roles first. Stored in `profile.gap_reviews` (one row per account: profile version, goals version, status `running|ready|failed`, error code, questions, skills, resolved).

The review is reused until the profile or goals change by any other way than the person's own kept answers, added skills and reordering, which carry it forward to the new version (no new call) and mark the question `kept`. Skills are checked against the positions again each time they are shown. Reading the strength never starts a review; the Profile & goals page and the Improve and Skills pages do.

No model configured, or the review failed (`ai_budget_reached`, `ai_daily_limit_reached`, `ai_failed`): the questions and skills say `unavailable` or `failed` with the problem code; the strength checklist still works. A failed review is not repeated by asking again; `POST /api/v1/profile/questions/review` starts it again (the spending limits still apply, so over one it fails again before any call).

## Draft from an answer
`POST /api/v1/profile/questions/{id}/draft { answer (1–2000 chars) }` → one small `complete` call with the question, the answer and the relevant profile part (the position, or headline/summary/positions/skills) → `{ items: [string], education? }`; the draft's `kind` (`highlights|label|summary|education|link`) comes from the question's section, not the model. **Draft source check** (`completion/check.rs`): every number, percentage, currency amount, acronym, technology name and capitalised word inside a sentence in a line must appear in the answer or the profile (the import source check's normalisation: no case, no whitespace, plain quotes and dashes; numbers whole; words of up to three letters whole). Lines that fail are dropped and counted (`dropped`, "1 line left out: it mentioned something you didn't write"). A school's fields are checked one by one (the school itself must be said, else there is no draft; dates with the import check's date forms); a link must be an address the answer writes. Limits: lines ≤ 300 characters, a headline ≤ 150, a summary ≤ 1200. Drafts live 24 h (`profile.drafts`; the answer itself is not stored) and a new draft replaces the earlier one for its question.

`POST /api/v1/profile/drafts/{id}/keep { items?, education? }` writes into the profile as a new version with source `answer`: highlights are appended to the position (repeats skipped), a headline or summary is set, a school or links are added. Edited lines are the person's own words and skip the check; they are validated for length. Refused with 409 `profile_changed` if the profile changed since the draft was made. `POST …/discard` deletes it. `POST …/questions/{id}/skip` marks the question skipped (not asked again for this review).

## Skills
`GET /api/v1/profile/skills/suggested` (from the gap review) → Add appends `{name}` to `skills`, in the order added; Not mine records it in `profile.skill_dismissals` so it is not suggested again. `PUT /api/v1/profile/skills/order { names }` puts the skills in the person's order (the names must be the profile's skills, each once); the first three drive the job board searches (#28), so the Skills page says so and has move up and move down buttons.

## Endpoints (session, OpenAPI)
`GET /api/v1/profile/strength`, `GET /api/v1/profile/questions` (202 while the review runs), `POST …/questions/review` (try again), `POST …/questions/{id}/draft`, `POST …/questions/{id}/skip`, `POST …/drafts/{id}/keep`, `POST …/drafts/{id}/discard`, `GET …/skills/suggested`, `POST …/skills/suggested/{name}/{add|dismiss}`, `PUT …/skills/order`. `GET /api/v1/today` gains `profile_strength`, `next_profile_action` (`improve|skills|import|goals`, none once strong) and `profile_questions` (open questions when a review exists).

## Client (prototype)
Profile & goals: strength card (score, bar, checklist with Add/Improve per part). Improve route `/profile/improve?q=<id>`, outside the app frame like the goals interview: context chip, question, why, answer box, Draft from my answer → draft block (Keep / Edit inline / Discard; a school has no inline edit), Skip, Finish later, progress "Question n of N · strength a% → b%". Skills page `/profile/skills`: the skills in order with move buttons, and the found skills with "in N roles", Add / Not mine. Today: strength card while `next_profile_action` is set, with Continue / Not now (hidden for 7 days, kept on the device). Keyboard: Enter in the answer box = Draft (Shift+Enter newline), Esc = Finish later. 4 languages; 375 + desktop.

## Cost
AI role: `complete`. Gap review: one call per profile/goals version (~2–4k tokens in, ~1k out; one more only if the answer is cut off), made when the person opens Profile & goals, Improve or Skills, never in the background on its own. Each draft: one small call (a cut-off retries once). All inside the existing per-account and instance spending limits; a call that would cross one is refused before it is sent, shows `ai_budget_reached` with a plain message, and is not retried until the person asks. Estimates are not shown (each call is tiny). Without a model nothing here calls one. Undo: nothing is written before Keep; a kept draft or added skill can be edited or removed in the profile.
